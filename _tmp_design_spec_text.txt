[1] 一、引言
[2] 1、编写目的
本文档为「学生宿舍管理系统（Student Dormitory Management System，简称 SDMS）」的系统说明书，面向系统管理员、宿舍管理员、运维人员以及后续参与二次开发的开发人员，全面说明系统的建设目标、总体架构、功能设计、数据库设计、接口设计与部署运行方式。通过本文档，读者能够了解系统各模块的业务职责与操作流程，掌握数据库表结构与接口约定，并能够独立完成系统的部署、启动与日常维护工作。
[2] 2、项目背景
高校学生宿舍管理工作涉及楼栋与房间资源、学生住宿分配、卫生检查、设施设备与维修、住宿费用收缴、公告通知与来访登记等大量日常事务。传统以纸质登记与电子表格为主的管理方式存在数据分散、更新滞后、统计困难、责任难以追溯等问题。为此，本系统以信息化手段对上述业务进行整合，构建覆盖宿舍资源分配与日常运营全流程的数字化管理平台，为管理员、宿管与学生提供统一的协作入口，提升管理效率与数据透明度。

[1] 二、系统概述
[2] 1、系统简介
本系统名为「宿舍事务管理系统」，英文名称为 Student Dormitory Management System（SDMS），是一套面向高校学生宿舍场景的前后端分离综合管理平台。系统以 Spring Boot 与 Vue 3 为主要技术路线，后端对外提供统一的 RESTful 接口，前端提供管理员门户、宿管门户与学生门户三套界面，覆盖从宿舍资源分配到日常运营的完整业务闭环，实现住宿分配、卫生检查、设施维修、费用收缴、公告发布与来访登记等业务的在线化处理。

[1] 三、系统总体设计
[2] 1、总体架构
系统采用前后端分离的 B/S 架构，自下而上划分为数据层、持久层、业务服务层、接口层与表现层五个层次。
数据层：采用 MySQL 关系型数据库，共 11 张业务表，统一采用逻辑删除策略，通过冗余字段维护业务关联。
持久层：以 MyBatis-Plus 作为 ORM 框架，Mapper 接口继承 BaseMapper 获得通用增删改查能力，配合分页插件实现物理分页，并通过元数据处理器自动填充创建时间与更新时间。
业务服务层：Service 接口继承 IService，ServiceImpl 完成业务校验、事务控制、状态流转与统计聚合等核心逻辑。
接口层：由 Spring MVC 控制器对外暴露 RESTful 接口，统一封装为 Result 响应对象，并由全局异常处理器统一转换异常信息。
表现层：基于 Vue 3 的单页应用，使用 Element Plus 组件库构建界面，Axios 统一发起请求，ECharts 渲染数据看板图表。
前后端通过 HTTP 与 JSON 进行数据交互。前端开发服务器将 /api 前缀的请求代理转发至后端 8080 端口，后端通过 WebMvcConfigurer 配置跨域访问规则与上传文件静态资源映射。

[1] 四、功能模块详细说明
[2] 1、登录认证与账号管理
认证模块由 AuthController 提供支撑，包含登录、注册、修改密码、重置密码与用户信息查询五类接口。登录时系统按用户名与密码匹配系统用户表，账号状态为禁用时拒绝登录并给出明确提示；登录成功后，若用户角色为学生，响应中额外附带该学生的档案信息，前端将其缓存至本地，供学生端各页面取用。学生注册时系统校验用户名与学号的唯一性，在同一事务中创建系统用户账号与学生档案，档案初始状态为待入住，账号默认角色为学生。修改密码需校验原密码正确性；忘记密码时通过用户名、学号与注册手机号三重校验后重置。个人中心支持查看与修改姓名、性别、手机号、邮箱等基本信息，并支持上传头像，头像文件按日期分目录存储并以 UUID 重命名，上传成功后回写用户表的头像字段。
[2] 2、首页数据看板
管理端首页看板由 DashboardController 提供数据支撑。总览接口一次性聚合房间总数、床位总数、已用床位、可用床位、学生总数、应收费用、已收费用、未缴笔数、待处理报修数与今日来访数等核心指标，前端以统计卡片形式呈现。看板同时提供六类统计图表：各楼栋入住率对比、学生学院分布、卫生检查等级分布、设施状态分布、房间状态分布与费用收缴情况，分别以柱状图与饼图渲染，并支持随浅色与深色主题自动重绘配色。页面底部展示最近若干条卫生检查记录。学生端首页则为欢迎卡片、住宿信息卡片、最新公告列表、快捷入口与未缴费用提醒，便于学生快速掌握待办事项。
[2] 3、宿舍楼管理
宿舍楼模块维护楼栋基础信息，包括楼栋名称、楼栋类型、楼层数、每层房间数、负责宿管与备注说明。模块支持楼栋的增删改查，删除采用逻辑删除，历史数据不会被物理清除。检索支持按楼栋名称模糊匹配、按楼栋类型与负责宿管精确筛选。新增或编辑楼栋时选择宿管后，系统自动回填宿管姓名，避免冗余字段手工填写出现不一致。模块还提供楼栋住宿统计接口，逐栋统计床位总数、已用床位与可用床位，为床位资源调度提供数据依据；楼栋详情接口则返回楼栋信息及其下属房间清单。
[2] 4、宿舍房间管理
房间模块以房间为核心对象，维护房间号、所属楼栋、所在楼层、床位容量、房间类型、状态与住宿费用等属性。数据库层以房间号与楼栋编号建立唯一约束，防止同一楼栋出现重复房间号。列表页支持按房间号、楼栋、房间类型与状态组合筛选，并以进度条直观展示每间房的入住率。房间的已入住人数在查询时依据在住学生数量实时重算，避免因增减住宿记录而产生脏数据。房间详情弹窗展示房间基本信息、当前入住学生名单与床位占用网格，管理人员可直接在床位网格中辨识可用床位，也可对在住学生办理退宿。模块另提供房间状态统计与按楼层统计两个接口，辅助管理人员掌握整栋楼的空置与维修情况。
[2] 5、宿管管理
宿管模块仅对管理员角色开放，用于维护宿管账号的增删改查并控制账号的启用与禁用状态。新增宿管时可设置初始密码，系统固定写入宿管角色；编辑时用户名不可修改且不展示密码项，避免误改登录凭据。列表支持按用户名、姓名、性别与账号状态组合检索。宿管账号被禁用后不可用于登录，但其负责楼栋的历史管理记录仍完整保留。
[2] 6、学生管理
学生模块维护学生档案，字段涵盖学号、姓名、性别、手机号、邮箱、学院、专业、班级、年级、身份证号以及住宿相关的楼栋、房间与床位信息。新增学生时后端自动同步创建登录账号，用户名取学号、初始密码统一设定，无需管理员另行开户；修改档案时同步更新登录账号中的姓名、性别、手机号与邮箱，保证两处数据一致；删除档案时级联移除对应的登录账号。列表支持按学号、姓名、性别、学院与年级组合检索，查看详情时同时返回档案信息与账号信息。模块另提供学院分布与年级分布两项统计接口，为数据看板提供学生结构数据，并可按房间查询室友名单。
[2] 7、住宿管理
住宿管理模块处理入住分配与退宿两项核心业务。分配住宿时，管理人员依次选择楼栋、房间与床位，系统对房间是否存在、是否已满员、是否处于维修状态以及目标床位是否已被占用进行逐项校验，任一条件不满足即拒绝分配并给出原因；校验通过后写入学生的楼栋、房间、床位与入住时间，档案状态置为已入住，同时递增房间已入住人数，人数达到容量上限时房间状态自动转为已满。办理退宿时系统清空学生的住宿字段并将档案状态置为已退宿，同时回退房间人数与状态。列表支持按学号、姓名、性别、楼栋房间与住宿状态组合查询，并支持查看学生详情。
[2] 8、卫生管理
卫生模块记录每次宿舍卫生检查的结果，包含检查房间、检查日期、评分、等级、检查人与备注。评分采用零至一百分制，提交时系统自动换算等级：九十分及以上为优秀，八十分及以上为良好，六十分及以上为合格，其余为不合格，修改评分时同样重新计算等级，避免人工填写出现等级与分数不符。检查人信息由系统根据当前登录用户自动填充。模块支持按房间号、楼栋、等级与检查人组合检索，并提供等级分布统计、各楼栋平均分统计与最近检查记录查询。学生端可查看本宿舍的历史检查记录，包含每次检查的日期、分数、等级、检查人与备注说明。
[2] 9、设施管理
设施模块建立宿舍设施设备台账，记录设施名称、设施类型、所属房间、购买日期、单价、状态与备注，类型涵盖家具、电器与其他三类。模块支持设施的增删改查，支持按名称、类型、房间与状态组合筛选，并提供设施状态统计与类型分布统计，其中状态统计同时汇总设施总价值，为资产盘点提供依据。学生端的「我的宿舍」页面会列出本房间配置的设施清单，学生发起报修时可直接从本房间设施列表中选择报修对象。
[2] 10、维修管理
维修模块以工单形式贯穿报修全流程。学生提交报修时选择本房间设施并填写问题现象，系统自动记录报修人与报修时间，工单状态置为待处理，同时将该设施状态标记为损坏。管理人员在处理工单时可将状态推进为处理中或已完成，已完成时可登记处理结果与实际维修费用；工单完成后设施状态自动恢复为正常，若维修费用大于零，系统自动生成一条维修费费用记录并关联至报修学生，缴费账期按报修时间顺延七天计算，学年与学期由系统依据当前月份自动判定。模块支持按设施名称、房间、报修人、状态与处理人组合检索，提供待处理、处理中、已完成三类状态的数量统计，学生端则可查看自己提交的全部报修工单及处理进度。
[2] 11、费用管理
费用模块由费用类型与费用记录两部分构成。费用类型定义收费项目，包含类型名称、类型编码、单价、计量单位、说明与启用状态；费用记录则关联学生、费用类型、金额、缴费状态、缴费方式、缴费时间、学年、学期与应缴日期。管理人员可为指定学生手工新增费用记录，也可由维修业务自动派生。缴费支持现金、微信、支付宝与银行卡四种方式，缴费时系统校验记录是否已缴，已缴记录不允许重复缴费并抛出业务异常。列表支持按学号、姓名、费用类型、学年、学期与缴费状态组合检索，提供收缴情况统计与近十二个月的月度收缴趋势。学生端以待缴费与已缴费两个标签页分类展示个人账单，待缴费记录可在线完成缴费操作。
[2] 12、公告管理
公告模块支持通知、公告与警告三类信息的发布与管理，字段包含标题、正文、类型、发布人、发布时间、状态与浏览量。公告支持草稿与已发布两种状态，仅已发布的公告对学生可见；查看公告详情时浏览量自动累加。模块提供按标题、类型、发布人与状态的组合检索，并提供公告类型分布统计。学生端首页与公告页展示最新公告列表，点击即可查看正文详情。
[2] 13、来访登记与系统特性
来访登记模块记录校外人员进出宿舍的情况，包含来访人姓名、联系电话、身份证号、来访事由、访问楼栋与房间、被访学生、到访时间与离开时间。登记时状态置为访问中，离开时登记离开时间并将状态置为已离开。模块支持按来访人姓名、联系电话、访问房间与状态组合检索，并提供访问统计，包含总访问量、在访人数、已离开人数、各楼栋访问分布以及近七天访问趋势。
系统层面还提供若干通用特性：界面支持浅色、深色与跟随系统三种主题，切换后图表配色同步重绘；管理端侧边栏可折叠，并配有面包屑导航；所有列表查询统一采用分页参数与统一响应结构；数据删除一律采用逻辑删除，配合自动填充的时间字段，保证业务数据可追溯。
[1] 五、数据库设计
[2] 1、数据库概述
数据库名称为 dormitory_db，字符集为 utf8mb4，排序规则为 utf8mb4_unicode_ci，存储引擎为 InnoDB，共包含 11 张业务表。所有业务表均包含 create_time、update_time 与 deleted 三个公共字段，其中 deleted 为逻辑删除标记，取值 0 表示未删除、1 表示已删除，由 MyBatis-Plus 全局配置统一维护，查询时自动追加过滤条件。各业务表之间不设置物理外键约束，关联关系通过冗余编号与名称字段在应用层维护，以提升查询效率并降低级联操作风险。

[2] 4、表间关系
各表之间的逻辑关联关系如下，关联通过应用层冗余编号与名称字段维护。
系统用户与学籍档案：sys_user.id 与 student_info.user_id 一一对应，一个登录账号对应一份学生档案。
宿舍楼与房间：building.id 与 room.building_id 一对多，楼栋信息同时冗余至房间表的楼栋名称字段。
房间与学生：room.id 与 student_info.room_id 一对多，学生的房间号、楼栋编号与楼栋名称同步冗余，便于按楼栋维度统计。
宿舍楼与宿管：building.manager_id 指向 sys_user.id 中角色为宿管的用户。
房间与卫生检查：room.id 与 hygiene.room_id 一对多，记录该房间的历次检查结果。
房间与设施：room.id 与 facility.room_id 一对多；设施与维修工单通过 facility.id 与 facility_repair.facility_id 关联。
学生与费用：student_info.id 与 fee_record.student_id 一对多；费用类型通过 fee_type.id 与 fee_record.fee_type_id 关联。
学生与来访：student_info.id 与 visitor.visited_student_id 一对多，记录被访学生信息。
用户与业务操作：sys_user.id 分别关联卫生检查的检查人、维修工单的报修人与处理人、公告的发布人以及来访记录的登记人。
为提升检索效率，数据库在角色、状态、楼栋、房间、日期等高频查询字段上建立了十五个普通索引。
[1] 六、接口设计
[2] 1、接口规范
系统接口遵循以下统一约定。
访问地址：后端服务根路径为 http://localhost:8080/api，所有接口均位于该路径之下。
数据格式：请求与响应均采用 JSON，日期时间格式为 yyyy-MM-dd HH:mm:ss，时区为 GMT+8。
统一响应：所有接口返回统一的 Result 结构，包含 code、message 与 data 三个字段，code 取值为 200 表示处理成功，非 200 表示业务失败，message 携带中文提示信息。
分页约定：分页查询统一接收 current 与 size 参数，分别表示当前页码与每页条数，响应封装为 PageResult，包含 records、total、size、current 与 pages 五个字段。
异常处理：由全局异常处理器统一捕获运行时异常与系统异常，业务异常直接返回其提示信息，未知异常统一返回系统异常提示，避免堆栈信息外泄。
跨域与上传：后端开放跨域访问并映射上传目录，单个文件大小上限为 10MB。

[1] 七、系统部署与运行
[2] 1、部署前准备
部署前需准备以下环境：安装 JDK 25 及以上版本并配置 JAVA_HOME 环境变量；安装 Apache Maven 3.10.0 并配置镜像仓库；安装 MySQL 26.0 及以上版本并启动数据库服务；安装 Node.js 26 及以上版本，确保 npm 可用。
[2] 2、数据库初始化
使用数据库脚本初始化库表结构与演示数据，执行方式如下：以 root 用户登录 MySQL，执行项目后端资源目录下的 dormitory_db.sql 脚本，脚本将自动创建 dormitory_db 数据库、11 张业务表、相关索引，并写入管理员、宿管与学生等演示数据。
[2] 3、后端配置与启动
打开后端资源目录下的 application.yml 配置文件，将数据库连接地址、用户名与密码修改为本地实际配置，同时按需调整文件上传目录。配置完成后，可在集成开发环境中直接运行启动类 DormitoryApplication，也可在项目后端目录下执行 Maven 的 spring-boot:run 命令启动服务。启动成功后后端服务监听 8080 端口，接口根路径为 /api。
[2] 4、前端启动
进入前端目录执行依赖安装命令，安装完成后执行开发启动命令，前端开发服务器默认监听 5173 端口，并将 /api 前缀的请求代理转发至后端服务。浏览器访问 5173 端口即可进入登录页面。如需生成生产环境静态资源，可执行构建命令，产物输出至前端 dist 目录。

[2] 6、注意事项
启动顺序上应先启动数据库，再启动后端服务，最后启动前端服务；若修改了数据库密码，需同步更新后端配置文件，否则后端启动时会因数据库连接失败而退出。前端代理目标端口应与后端实际监听端口保持一致。上传目录需保证应用具备写权限，否则头像上传与文件上传会失败。若前端端口被占用，可在 Vite 配置中调整端口或关闭占用程序。
[1] 八、总结
本系统围绕高校学生宿舍管理场景，完成了从数据库建模、后端接口设计到前端界面实现的完整开发流程，形成了一套包含十三个功能模块、十一个控制器、十一张业务表的前后端分离应用。系统通过角色划分实现了管理员、宿管与学生三类用户的差异化功能门户，通过统一的响应结构、分页约定与全局异常处理保证了接口的一致性与健壮性，通过逻辑删除与时间字段自动填充保证了业务数据的可追溯性，通过实时重算房间入住人数、自动换算卫生等级、自动生成维修费用等规则设计减少了人工维护成本。
同时，系统在以下方面仍有改进空间：认证目前基于用户名与密码明文比对，尚未引入令牌机制与后端接口级权限校验，权限控制主要依赖前端路由守卫；数据查询未引入缓存，统计类接口在数据量增长后可能面临性能压力；系统尚未提供数据导入导出、操作日志审计与消息通知能力。后续可在服务端补充令牌鉴权与接口级权限拦截，引入缓存组件优化统计查询性能，并扩展报表导出与操作审计功能，进一步提升系统的安全性与完整性。
