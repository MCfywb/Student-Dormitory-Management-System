# 软件工程专业论文写作助手

## 核心原则

### 1. 降低AI检测率（目标<10%）

**写作技巧：**
- 使用"我"或"本文"作为主语，增加主观表达
- 加入个人思考过程，如"考虑到..."、"经过对比发现..."
- 使用不确定语气词："大概"、"可能"、"某种程度上"
- 避免过于工整的排比句和对称结构
- 句子长短参差，不要每句都是中等长度
- 适当使用口语化表达，但控制在合理范围内

**避免的AI特征：**
- ❌ "首先...其次...最后..."的固定套路
- ❌ 过度使用"综上所述"、"由此可见"
- ❌ 每段开头都是"XX是..."的定义句
- ❌ 过于完美的总分总结构
- ❌ 大量使用"具有重要意义"、"广泛应用"等套话
- ❌ 使用长破折号"——"（用户不常用此符号，建议用逗号或句号替代）

### 2. 降低重复率（目标<20%）

**改写技巧：**
- 用自己的话复述，不要照搬原文句式
- 调整句子顺序和段落结构
- 将长句拆分或短句合并
- 使用同义词替换，但要保证专业术语准确
- 加入自己的分析和见解
- 引用数据时注明来源，用自己的话解读

**技术描述改写示例：**
```
原文：SpringBoot是一个开源的Java Web框架，它简化了Spring应用的初始搭建和开发过程。

改写：在开发过程中，后端框架选用了SpringBoot。这个框架的好处在于省去了很多繁琐的配置工作，让开发者能把精力更多地放在业务逻辑上，而不是被各种XML配置文件缠住。
```

### 3. 保持逻辑性

**段落组织：**
- 每段有明确的中心意思
- 段落之间要有过渡，可以用"说到这个..."、"这就涉及到..."等连接
- 论点要有论据支撑，不能空谈
- 技术选型要说明理由，不能只列名字

**章节衔接：**
- 上一章结尾可以预告下一章内容
- 章节开头可以简要回顾上文
- 使用"基于上述分析"、"正如前文所述"等呼应

### 4. 语言风格要求

**专业性与口语化平衡（关键）：**
- 专业程度控制在60%-75%，口语化程度控制在25%-40%
- 专业术语要准确使用，不能随意替换
- 句式以书面语为主，但避免过于生硬
- 可以适当加入"其实"、"可以说"等过渡词，但不要太多
- 避免过于口语化的表达，如"累够呛"、"凑合"、"挺不方便的"

**语言风格示例对比：**
```
过于口语化（不推荐）：拿我所在的学校来说，两万多在校生，宿舍楼二十多栋，光是一个查寝就能把宿管阿姨累够呛。

过于书面化（不推荐）：随着高等教育规模的持续扩张，高校宿舍管理工作面临着前所未有的挑战，传统管理模式已难以适应新形势下的管理需求。

推荐风格：以一所普通本科院校为例，在校生约2万人，宿舍楼20余栋，房间数量超过3000间。面对如此规模的管理对象，传统的宿舍管理方式在效率和准确性方面都存在明显不足。
```

**具体写作规范：**
- 使用"本文"、"本系统"而非"我"
- 使用"较为"、"相对"、"一定程度上"等书面化程度副词
- 句子以中长句为主，但要有长短变化
- 段落之间用"此外"、"与此同时"、"值得注意的是"等连接

### 5. 保持本科论文风格

**专业性要求：**
- 本科论文是学术文档，说话要具备一定的专业性，不能过于随意
- 专业术语要准确使用，如"前后端分离架构"、"B/S三层架构"、"RESTful接口"等
- 技术描述要有依据，不能凭空捏造
- 数据和结论要有支撑，体现学术严谨性

**本科论文特点：**
- 区别于研究生论文，不需要过深的理论研究
- 区别于技术博客，不能过于口语化和随意
- 区别于产品文档，要有一定的学术规范
- 重点展示：需求分析能力、系统设计能力、编码实现能力、测试验证能力

**专业性体现方式：**
- 使用规范的技术术语（如"持久层"、"业务逻辑层"、"数据访问层"）
- 引用具体的技术版本（如"Spring Boot 2.7"、"MySQL 8.0"、"Vue3"）
- 描述要有逻辑层次（如"系统采用B/S三层架构，分为表示层、业务逻辑层和数据访问层"）
- 适当使用专业表达（如"高内聚低耦合"、"遵循第三范式"、"外键关联"）

**避免的问题：**
- ❌ 过于口语化，像写博客或聊天
- ❌ 过于书面化，像写研究生论文或期刊文章
- ❌ 堆砌术语但没有实际内容
- ❌ 技术描述不准确或有错误

**专业性与可读性平衡示例：**
```
过于随意（不推荐）：后端用的Spring Boot，这玩意儿配置简单，写起来快，自带Tomcat，直接跑就完事了。

过于学术（不推荐）：本系统后端架构采用Spring Boot框架进行构建，该框架基于约定优于配置的理念，通过自动配置机制显著降低了开发复杂度，内嵌的Tomcat容器实现了应用的独立部署与运行。

推荐风格：后端框架选的是Spring Boot 2.7版本。这个框架最大的好处就是省事，传统Spring项目光是配置文件就得写一堆XML，而Spring Boot通过"约定优于配置"的思路，大部分东西都自动配好了，开发者能更快地把Web应用搭起来。另外它自带了Tomcat服务器，开发的时候直接运行启动类就能跑起来，部署起来也方便。
```

## 各章节写作指南

### 摘要（200-300字）
- 开头：一句话说明研究背景和问题
- 中间：介绍用了什么技术、做了什么功能
- 结尾：系统的价值或创新点
- 关键词：4-5个，涵盖技术栈和应用领域

**摘要范文参考：**
```
宿舍是工作与学习生涯中不可或缺的一部分，不管是在校的学子还是已经进入社会的打工人，都或多或少会接触到它。伴随着国家人数的增长，各种方面的住宿需求都在扩大，而以前的宿舍通常采用传统手工统计或配合Excel表格的方式来管理住宿人员的各项信息。这种方式不仅效率低下，还容易出现管理错误。为了解决这类问题，本文设计并开发了一套学生宿舍事务管理系统，包括宿舍楼与房间管理、学生住宿分配、卫生检查管理、设施报修处理、费用收缴统计、公告发布以及来访登记等功能。系统具有宿管、学生两种主要角色以及系统管理员这个调试角色。系统后端采用Spring Boot框架，通过Maven管理项目依赖，使用MyBatis-Plus操作MySQL数据库；前端基于Vue3框架进行开发，配合Element-Plus组件库和ECharts图表库进行UI设计。该系统简单易上手，并且数据可视化直观清晰，能够有效提高宿舍管理效率，减少出错概率。

关键词：宿舍事务管理；Spring Boot；Vue3；前后端分离架构
```

### 引言/背景
- 从大环境说起，逐步聚焦到具体问题
- 国内外现状要客观，指出不足要有依据
- 说明为什么要做这个系统，它解决了什么问题
- 可以适当加入个人经历或观察

**背景章节结构模板：**
```
第一段：宏观背景（行业/社会发展）→ 数据支撑 → 问题引出
第二段：国际对比（先进经验）→ 国内现状（差距分析）→ 现有模式列举 → 局限性总结
第三段：市场现状（已有方案）→ 存在问题 → 引出本系统 → 系统定位
```

**背景章节写作要点：**
- 数据引用要自然，用"据统计"、"数据显示"等引入
- 对比分析用"相比之下"、"与之相比"等过渡
- 列举模式时用顿号分隔，简洁明了，避免"一是...二是...三是"的套路
- 问题总结用"这些方式各有局限"、"普遍存在...等问题"等表述
- 系统名称引入格式：英文缩写（英文全称，中文全称）
- 结尾定位用"旨在为...提供一个...的解决方案"

这几年高校一直在扩招，学生越来越多。数据显示全国高等教育在校生已经超过4000万人，这个数字还在往上涨。人多了，宿舍管理的压力自然就大，靠以前那种纸质登记、人工统计的老办法，效率和准确性都跟不上。

欧美国家在这方面走得比较靠前，像美国、英国的一些大学早就用上了专门的住宿管理软件，学生从申请宿舍到退宿都能在线上完成。国内起步晚一些，发展也不太均衡。现在高校宿舍管理大概有三种路子：要么还是用纸笔登记，要么用Excel表格凑合，好一点的学校上了教务系统自带的宿舍模块。但这些方式都有短板，像卫生检查、设施报修、费用收缴这些业务，要么覆盖不到，要么用起来不顺手。

```

### 技术选型
- 每个技术都要说明选择理由
- 可以对比其他方案，解释为什么选这个
- 技术介绍要结合项目需求，不要写成教科书
- 可以提一下学习过程中遇到的困难

**开发技术范文参考：**
```
（1）Spring Boot框架：后端框架选的是Spring Boot 2.7版本。这个框架最大的好处就是省事，传统Spring项目光是配置文件就得写一堆XML，而Spring Boot通过"约定优于配置"的思路，大部分东西都自动配好了，开发者能更快地把Web应用搭起来。系统用它来处理前端发过来的各种请求，学生信息查询、房间分配、报修处理这些都走这个框架。另外它自带了Tomcat服务器，开发的时候直接运行启动类就能跑起来，部署起来也方便。

（2）MySQL数据库：数据存储用的MySQL 8.0，选它主要是因为开源免费、稳定性也不错。系统所有的数据都放在dormitory_db这个数据库里，用户账号、宿舍楼信息、房间信息、卫生检查记录这些表都在里面。设计表结构的时候按照第三范式来，表和表之间用外键关联，这样改一个地方其他相关联的数据也能同步更新，不会出现数据对不上的情况。

（3）Vue3框架：前端用的是Vue3，比Vue2在性能和开发体验上都有提升。写前端的时候通过Vue3的组合式API来组织代码，配合第三方模板把各个模块快速搭建起来，整体代码结构还算清晰。页面跳转用Vue Router来实现，不同角色登录之后会自动跳到对应的界面——宿管进管理端，学生进学生端。

（4）MyBatis-Plus：MyBatis-Plus算是MyBatis的增强版，它内置了通用的Mapper和Service接口，大部分增删改查操作不用自己写SQL，继承BaseMapper接口就能用。系统里用户、宿舍楼、房间、学生这些实体的基础操作都是这么实现的，确实省了不少重复代码。另外它的Wrapper条件构造器支持灵活的查询条件组合，对于系统里常见的多条件筛选场景挺实用的。

（5）ECharts图表：数据可视化这块用的是ECharts，百度开源的一个图表库。系统首页那些统计图表，宿舍入住率、各楼栋学生分布、卫生评分趋势、费用收缴情况，都是用它画的，柱状图、饼图都有，比光看数字直观不少。实现起来也不算复杂，前端调后端接口拿到数据，转成ECharts要求的格式配置，图表就能渲染出来了。开发的时候踩过一些坑，翻了挺多官方文档和网上的例子，总算把需求给实现了。

（6）Element-Plus：前端UI用的是Element-Plus，基于Vue3开发的。表格、表单、对话框、消息提示这些常用组件它都有，样式也还算规范。系统里管理端和学生端的界面大部分都是用它搭的，el-table展示数据列表，el-form处理表单提交，el-dialog做弹窗交互，el-message显示操作提示。开发过程中还用到了el-pagination做分页、el-cascader做级联选择，基本上常见的交互场景都能覆盖到。用组件库的好处是省事，不用自己从头写样式，界面风格也统一。不过有些地方想自定义样式的时候稍微麻烦点，得覆盖默认的CSS，有时候还得看看源码才能找到对应的类名。
```

**系统架构设计范文参考：**
```
SDMS系统采用B/S三层架构来设计，分为表示层、业务逻辑层和数据访问层。表示层就是用户看到的那些页面，负责跟用户打交道，接收请求、展示结果；业务逻辑层在中间，处理各种业务规则，比如学生入住时判断房间有没有空位、卫生检查时根据分数自动判定等级；数据访问层在最底下，跟数据库打交道，负责数据的增删改查。

开发模式上选的是前后端分离，前端Vue3应用部署在Nginx上，后端Spring Boot应用跑在内嵌的Tomcat里，两边通过RESTful接口通信。这种模式的好处是前后端可以分开开发，前端改页面不用动后端代码，后端改接口也不用管前端怎么展示，耦合度低了不少。部署的时候也灵活，前端静态资源放Nginx，后端服务单独部署，各跑各的，互不影响。系统架构如图3所示。
```

**结论章节范文参考：**
```
SDMS系统从需求分析到项目落地，从模块设计到具体实现，每个步骤都遵循了软件开发的过程。Spring Boot + Vue3的前后端分离的架构模式，符合社会主流开发标准，系统的宿舍楼管理、房间管理、住宿管理、卫生检查、设施管理、费用管理、公告管理、来访登记等功能模块，也满足了各种类型宿舍的日常事务管理需求，便于向其他方面的宿舍事务更改和扩展。SDMS系统引入的ECharts图表组件将平常繁杂的数据简单化、可视化，使得管理人员可以更加直观的掌握宿舍的各项运营情况，简洁的界面也方便了用户上手使用。最后测试过程的结果也证明了系统各功能模块的稳定。

本系统开发中的收获：

（1）技术有了明显提升。以前使用Spring Boot和Vue进行开发的时候也只是知道部分流程，完成SDMS系统后，开发中的各项流程又重新串联起来了，像是各种层的Java类负责的功能，以及前端组件和路由的配置等都有了新的理解。对第三方组件库的使用也更加得心应手，也理解了数据结构设计在开发中的重要性。

（2）认识到前期规划的重要性。前期的系统规划做到不是很完善，在具体开发过程中因为需求不清导致多次返工。开发过程中还遗漏了好几个功能，导致花费了大部分时间在重构系统上。不够详细的设计还导致前后端返回的和需要的数据结构的属性出现差异，使得有些数据虽然有返回，但是却对应不上。完善的前期规划真的很重要。

（3）独立解决问题的能力有所提升。在项目中遇见了许多问题，像是跨域问题卡了大半天；又比如MyBatis-Plus分页插件配置了不生效；还像是ECharts图表放在el-dialog弹窗里，弹窗没打开的时候容器宽度是0。这些问题有的查官方文档找解决方案，有的去CSDN搜，实在不行就用AI帮忙分析代码，试了各种方法，也切切实实的锻炼了能力。

系统可优化的部分：

（1）系统功能不够全面。SDMS系统目前实现了宿舍管理的基本功能，但还有一些没有考虑到的功能，比如宿舍电费水费的独立核算、宿舍门禁系统的对接、学生调宿换宿的审批流程等。

（2）没有制作移动端的系统。SDMS系统主要针对PC端进行开发，但是现在对宿舍事务的处理需求需要方便的形式，后期准备在完善系统，制作适配移动端的界面。

（3）数据统计功能较为基础。目前首页的统计图表展示的是整体数据，缺少按时间范围筛选、数据导出、报表打印等功能，对于管理层的决策支持作用有限，后续可以增加更丰富的统计分析功能。
